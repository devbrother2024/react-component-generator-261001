# TDD Rule

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 해석의 여지를 찾지 말고 문자 그대로 따른다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 적용되는 **기본값(fallback)**이다.

## 적용 기준

### TDD 필수

- **비즈니스 로직** (도메인 규칙, 상태 전이, 계산)
- **API** (엔드포인트, 요청 검증, 응답 형태, 에러 처리)
- **유틸리티 함수** (파싱, 변환, 정규화, 포맷팅)
- **버그 수정** — 버그를 재현하는 실패 테스트부터 작성한다

### TDD 불필요

- 타입 정의 (`type`, `interface`)
- 설정 파일 (빌드·린트·번들러·환경 설정)
- 순수 UI (로직 없는 마크업·스타일)
- SQL (스키마, 마이그레이션)

판단이 애매하면 **필수 쪽으로 분류**한다.

## RED-GREEN-REFACTOR 사이클

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 작성 후 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"**이어야 한다. 오타·import 오류·문법 오류로 인한 실패는 RED가 아니다 — 고치고 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 검증하지 않는다. 테스트를 다시 작성한다.

### 2. GREEN — 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 테스트가 요구하지 않는 분기·옵션·일반화를 추가하지 않는다.
- **신규 테스트 + 기존 테스트 전부 통과**를 실행으로 확인한다.

### 3. REFACTOR — 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 변경할 때마다 테스트를 실행해 **green을 유지**한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 RED로 돌아간다.

### 4. 반복

- 다음 동작에 대해 **RED부터** 다시 시작한다.

## 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 클립보드 보관 모두 포함한다.
- 삭제한 코드를 보면서 다시 타이핑하지 않는다. 테스트가 구현을 이끌게 한다.

## 변명 차단표

| 변명 | 반론 |
| --- | --- |
| "너무 단순해서 테스트 불필요" | 단순하면 테스트도 30초면 쓴다. 단순한 코드일수록 경계값 버그를 놓친다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현을 확인할 뿐 설계를 이끌지 못하고, 대부분 쓰이지 않는다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 더 오래 걸린다. 시간이 없을수록 TDD다. |
| "삭제하면 낭비" | 매몰 비용이다. 테스트 없이 쓴 코드는 검증되지 않은 부채이며, 다시 쓰는 비용이 더 싸다. |
| "프로토타입이다" | 프로토타입은 거의 항상 프로덕션이 된다. 진짜 버릴 코드라면 이 규칙 대상이 아닌 별도 브랜치에서 쓰고 버린다. |
