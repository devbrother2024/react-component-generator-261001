# commit: 변경사항 분석 후 컨벤션 커밋

변경사항을 읽고, 논리적 단위로 묶고, 단위마다 한국어 커밋 메시지를 작성해 **묻지 않고 바로** 커밋한다.

## 1. 변경사항 파악

다음을 실행해 전체 그림을 잡는다.

```bash
git status --short
git diff --stat            # 아직 스테이징 안 된 변경
git diff --cached --stat   # 이미 스테이징된 변경
git log --oneline -10      # 기존 메시지 스타일 참고
```

- 파일별 실제 내용은 `git diff <path>` / `git diff --cached <path>`로 읽는다. stat만 보고 메시지를 쓰지 않는다.
- 추적되지 않은 새 파일(`??`)은 diff에 안 나오므로 직접 읽어서 내용을 확인한다.
- 변경이 하나도 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- 사용자가 이미 일부를 스테이징해 두었다면, 그 스테이징을 의도로 존중한다. 스테이징된 묶음을 첫 번째 단위로 제안하고 임의로 풀지 않는다.

### 커밋하면 안 되는 파일

다음은 단위에서 빼고, 왜 뺐는지 사용자에게 알린다.

- 비밀 정보: `.env`, `*.pem`, `*.key`, 자격 증명·토큰이 담긴 파일. diff 안에 API 키처럼 보이는 문자열이 있어도 멈추고 알린다.
- 빌드 산출물·의존성: `dist/`, `build/`, `node_modules/`, `.DS_Store` 등 `.gitignore`에 있어야 할 것.
- 임시·디버그 파일: 이름이 `__`로 시작하는 임시 파일, `console.log`만 추가된 디버그 흔적.

## 2. 논리적 단위로 분류

"이 커밋 하나만 되돌려도 말이 되는가"를 기준으로 나눈다.

- **같은 의도의 변경은 한 커밋**: 기능 하나와 그 테스트, 그 기능을 위해 고친 타입은 함께 묶는다.
- **다른 의도는 나눈다**: 기능 추가와 무관한 리팩터링, 의존성 업데이트, 설정 변경은 각각 따로.
- **한 파일에 여러 의도가 섞여 있으면** `git add -p`가 대화형이라 쓸 수 없으므로, 억지로 쪼개지 말고 주된 의도의 커밋에 포함시킨 뒤 메시지 본문에 함께 적는다.
- 변경이 작고 의도가 하나면 커밋 하나로 충분하다. 쪼개기 위해 쪼개지 않는다.

## 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<본문 (선택)>
```

| type | 쓰는 경우 |
|---|---|
| `feat` | 사용자가 체감하는 새 기능, 화면·동작 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로, 구조·가독성 개선 |
| `chore` | 빌드·의존성·설정·문서·스킬 등 그 밖의 작업 |

요약 줄 규칙:
- 50자 안팎, 마침표 없음, "~ 추가 / ~ 수정 / ~ 개선"처럼 명사형으로 끝낸다.
- 무엇을 했는지보다 **왜·무엇이 달라지는지**가 드러나게 쓴다.
  - 나쁨: `fix: App.css 수정`
  - 좋음: `fix: 모바일에서 입력창이 화면 밖으로 넘치는 문제 수정`
- 본문은 요약만으로 이유가 안 보일 때만 쓴다. 바뀐 내용을 2~4줄 bullet로 적는다.

저장소 루트의 CLAUDE.md·AGENTS.md나 시스템이 커밋 메시지 끝에 붙이라고 지정한 줄(예: `Co-Authored-By:`)이 있으면 그대로 따른다.

## 4. 계획 알리기

승인을 묻지 않는다. 커밋을 시작하기 전에 계획을 한 번 보여주고 곧바로 5단계로 넘어간다.

```
커밋 1/2  feat: 레트로 계산기 테마로 메인 화면 디자인 개선
  - src/App.css, src/index.css, src/App.tsx, index.html
커밋 2/2  chore: commit 스킬 추가
  - .claude/skills/commit/SKILL.md
제외: .env (비밀 정보)
```

다만 다음 경우에는 커밋하지 않고 멈춰서 사용자에게 알린다.
- diff에 API 키·토큰처럼 보이는 문자열이 있을 때
- 변경 의도를 diff만으로 판단할 수 없어 메시지를 지어낼 수밖에 없을 때

## 5. 커밋 실행

계획한 단위를 순서대로 커밋한다.

```bash
git add -- <단위의 파일들>        # 파일을 명시적으로 지정. git add -A / . 금지
git commit -m "$(cat <<'EOF'
feat: 요약

- 본문
EOF
)"
```

- 각 커밋 전에 `git diff --cached --stat`으로 의도한 파일만 올라갔는지 확인한다.
- pre-commit 훅이 실패하면 `--no-verify`로 우회하지 않는다. 실패 내용을 보여주고 남은 커밋을 멈춘다.
- `--amend`, `push`, `reset`, `rebase`는 사용자가 따로 요청할 때만 한다.

결과가 마음에 들지 않으면 되돌릴 수 있도록, 끝나면 `git log --oneline -<커밋 수>`로 결과를 보여주고, 남은 미커밋 변경(제외한 파일 포함)이 있으면 함께 알린다.
